# fleet design

## What this is and is not

A CLI that runs and coordinates coding agents in herdr; not an agent itself, not a service, not a Go library.

## Model

Three roles. A **thread agent** (`thread-<slug>`, role `thread`) is one conversation on a Slack thread; it starts jobs and is the only agent that talks to people. A **lead** (`<job>-lead`) runs one job and starts workers. A **worker** (`<job>-<name>`) does one task for its lead. Thread agents are started by `fleet inbox`, the fednet client's hook, when a message arrives on a thread without a live agent; they run in the herdr workspace `threads`, one tab per thread, in `~/cross-repo/threads/` (default target) or `~/dev/<target>`. A **thread** has at most one live agent and, with a Linear team configured for the target, one thread ticket for its whole life; each conversation on it is a session, counted on the thread's row, ended by `fleet thread end`.

A **job** is the unit of work, named by its id, with at most one parent issue in Linear. It is a row in the `jobs` table from `job start` until `job end`; its lead and workers are rows in `agents`. A job is single-repo (`--repo`: the lead runs in `~/dev/<repo>`, read-only by convention) or cross-repo (the lead runs in `~/cross-repo/<job>/`, which fleet makes and removes). No command makes a worktree for an agent; agents open theirs with `fleet worktree`, and a worker runs wherever its lead's `--cwd` says.

A **target** names one ledger and one herdr session: `FLEET_TARGET`, `default` when unset or empty. A development machine has one target; a machine that hosts several datasets has one per dataset. The repo of a job is a job attribute, not the ledger key. A target's own settings (what no repo can hold: the Linear team of thread tickets, the fednet socket) are in `$XDG_CONFIG_HOME/fleet/<target>.json`.

## Parts and how they connect

- `cmd/fleet`: parses the command line (standard `flag`, one `FlagSet` per command, `--session` global, `job` (with `start`, `list` and `end`) and `thread` command groups) and dispatches to `internal/cmd`; turns a failure into `fleet: <message>` on stderr and the exit code.
- `internal/cmd`: one file per command, plus `agent.go` with what the two starters share (names, the task file, the config and Linear settings of a job, the work order, places in herdr, starting Claude Code and getting it past the folder-trust prompt to its input box, delivery, the machine's resources). `job start` runs its checks, does the Linear steps (parent created with `--new-parent`, parent claimed for the lead, lead's work order created and claimed), writes the job row and the lead's `starting` row, makes the cross-repo directory and the workspace, starts the lead and delivers the task. `spawn` (lead only) does the same for a worker in a tab of the job's workspace, with the job's parent issue from the jobs row. `send` adds the `[FROM: <agent>]` header and delivers through `herdr.Prompt`. `done` (workers only) delivers the report to the lead and ends the caller's row only when herdr reports it delivered; with `FLEET_ISSUE` it first writes the report to that issue and releases it through `internal/atb`. `worktree` opens `~/wt/<repo>/<job>[-<name>]` from origin/HEAD and records it in the target's ledger. `job end` (the lead, from its own pane; refused while the job has live workers) writes the report to the lead's work order and releases it, writes the conclusion to the parent issue and releases it, closes the other agents of the job's workspace, refuses while any agent but the lead has its cwd inside a recorded worktree or the cross-repo directory, removes them, ends the job with its outcome and the lead's row, hands the conclusion to `concluded` (the home-thread hook; it prints until thread agents exist) and closes the workspace last. `job end <job> --force` (a thread agent, or no `FLEET_ROLE`) reclaims a job from outside: no report, no Linear step; it closes the workspace first, cleans up with the same checks, and ends the job as `abandoned` with its live rows. `status` prints the open jobs as `job list` does, then the live rows joined with `herdr agent list`. `job list` joins the open jobs with their live lead and workers. `watch` (for cron) reads each live lead's and worker's herdr status, `state_change_seq` and a hash of its screen with Claude Code's spinner, input box and footer stripped, records them, counts an agent unchanged for the stale limit (or gone from herdr) as a suspect, prints every suspect, and tells each lead as `cron` through `send`'s path only when the set of suspects among that lead's workers changes; a lead's own suspicion is only printed.
- `internal/cmd/inbox.go` and `thread.go`: `inbox` reads the event file, reserves the `msg_id` in the target's ledger (a delivered or dropped message exits 0 at once), and routes: a live thread agent gets the message through `Deliver` headed `[FROM: inbox]`; a live row whose agent herdr no longer has is ended; otherwise `threadStart` reserves the agent's row and counts the session, does the Linear steps (new thread: ticket created with `atb linear create --label thread` and claimed; known thread: claimed again, a `Session <n> started` comment, the `Session <n> ended` comments read with `atb linear query`), makes the tab in the `threads` workspace (the workspace when missing), starts Claude Code as `spawn` does and delivers the embedded prompt (`thread_prompt.md`) with the channel context, the summaries and the message. A failed Linear step means Linear is unavailable: the row is ended, the message dropped, one line posted with `fednet client post`, exit 0. `thread end` writes the summary comment, releases the ticket, ends the row and closes the tab last, each step recorded through `runStep` (`steps.go`) so a retry continues; `thread set-project` and `thread relate` act on `FLEET_ISSUE`.
- `internal/cmd/askhuman.go`: `ask-human` records the question as pending (table `questions`) and takes it to the job's home thread through `route`, headed with the lead's name, so a thread agent is started for the thread when none is live; a thread agent's own question is only recorded. `inbox` marks a thread's pending questions answered when a person's message arrives there.
- `internal/herdr`: runs the `herdr` CLI with a bounded environment and a deadline, parses its one-object JSON reply, and maps `agent prompt` outcomes to the exit codes.
- `internal/atb`: runs `atb linear create` (only an identifier and an https URL are taken from its `--json` output), `claim`, `comment`, `release`, `set-project`, `relate` and `query` through herdr's runner (deadline, process group, allow-list plus `LINEAR_API_KEY`, `LINEAR_API_KEY_CMD`, `LINEAR_API_URL`, `ATB_HOME`); the key travels only in the environment, and atb's output never goes into an error.
- `internal/fednet`: runs `fednet client post` through the same runner; what fleet itself says in a thread.
- `internal/config`: a repo's `.fleet/config.json`, read from its main checkout `~/dev/<repo>`, and a target's `<target>.json`; standard library only. Unknown keys and wrong types are refused, naming the key.
- `internal/db`: the ledger (`modernc.org/sqlite`, WAL, 5 s busy timeout, immediate transactions) and its schema migration.
- `internal/identity`: the caller's identity from the `FLEET_*` variables; `FLEET_THREAD` is injected only into a thread agent's pane.
- `internal/exit`: the exit-code contract and the failure type every command returns.
- `internal/cliargs`: the clap-like behaviors `flag` lacks (flags after positionals, a string flag that records whether it was given).

## Invariants

Each invariant links to the test that guards it, or is marked untested.

- The CLI behaves as the judge (`judge/`) says: argv, exit codes, stdout/stderr, ledger rows, herdr state and screens. Guarded by `judge/run.sh`; every command's cases are in `judge/usage.sh`, `send.sh`, `lifecycle.sh`, `watch.sh` and `worktree.sh` and `thread.sh`.
- `inbox` is idempotent by `msg_id`: the message is reserved before anything else, a message once delivered or dropped is never acted on again, and a rerun while the thread's agent row is live (a run killed after the start) delivers to that agent instead of starting another; one live thread agent per thread is a partial unique index. Guarded by `cmd/fleet/thread_test.go`, `internal/db/db_test.go` and `judge/thread.sh`.
- An ending (`thread end`) can always be finished: a retry skips the recorded steps and continues, and `--force` finishes the local cleanup when Linear keeps failing, naming what is left. Guarded by `cmd/fleet/thread_test.go` and `judge/thread.sh`.
- A Linear step failing in `inbox` starts no agent; the message is acknowledged (dropped, exit 0) only once the thread has been told, else it is kept for fednet's retry. Guarded by `cmd/fleet/thread_test.go` and `judge/thread.sh`.
- A start reserves its ledger rows first, in one immediate transaction with the dedup checks (`job start`: the job row and the lead's `starting` row; `spawn`: the worker's `starting` row), then does the Linear steps (`job start`: parent, parent claim, work order, claim; `spawn`: work order, claim), and creates nothing else before they are done; an identifier is written onto the rows as soon as its issue exists, before the claim, so a failure after the reservation lists the rows, which keep the identifiers written so far, and `fleet job end <job> --force`; the key never appears in an argument, output or error. Guarded by `cmd/fleet/workorder_test.go`.
- One live lead per parent issue, one open job per name and per key in a target: two starts cannot both pass, even concurrently, because the reservation serializes them and the partial unique indexes refuse what slips through; a parent created by `--new-parent` is bound to the rows before anything else happens; the second is refused naming the first, and a parent whose lead ended is reused. Guarded by `cmd/fleet/workorder_test.go` (a start held at its parent claim, given or just created, while another is refused) and `internal/db/db_test.go` (the indexes).
- Every refusal of `job start` and `spawn` happens before any row is written, any Linear issue created or claimed, and anything made in herdr; the checks before the reservation read only (`herdr agent list`, `herdr workspace list`, `atb linear query`). Guarded by `cmd/fleet/lifecycle_test.go`.
- `job end` removes nothing an agent (other than the lead ending its job) is still in, and never a worktree with uncommitted changes; a lead's `job end` changes nothing in herdr, and nothing in the ledger but the record of its completed Linear steps, before those steps succeeded; a retry after a failure skips the recorded steps (`runStep`), never repeating a release, and only the record counts as done (atb's refusal of an issue nobody holds is a failure); a lead whose ending marked the job ended but failed to close the workspace may run `job end` again to finish. `job end --force` finishes the local cleanup whatever Linear did, and prints the Linear steps of the open job's ending that are not recorded. Guarded by `cmd/fleet/worktree_test.go` and `lifecycle_test.go` (a stateful retry).
- `watch` tells a lead only about its own workers, and only when their suspect set changes; a blocked or missing lead is told again next run. Guarded by `cmd/fleet/watch_test.go`.

## Interfaces

What the judge and the tests pin down:

- Commands `inbox`, `thread end`, `thread set-project`, `thread relate`, `ask-human`, `job start`, `job list`, `job end`, `spawn`, `send`, `done`, `status`, `watch`, `worktree`, with `--session <name>` global and `--help` on each; `--version`.
- Exit codes, shared by every command: 0 ok; 1 usage error or precondition refused; 2 no clear signal from herdr (timeout, stalled); 3 target blocked or a start stopped at an unknown screen; 4 target not found; 5 environment error (herdr, atb, git, database).
- Identity from `FLEET_AGENT`, `FLEET_ROLE` (`thread`, `lead`, `worker`), `FLEET_PARENT`, `FLEET_TARGET`, `FLEET_JOB`, `FLEET_ISSUE` (the work order or thread ticket, empty without one), injected into every pane a start creates, plus `FLEET_THREAD` (the thread key) in a thread agent's pane only; `FLEET_WATCH_STALE_SECS` overrides watch's 30-minute limit.
- The ledger at `$XDG_STATE_HOME/fleet/<target>/fleet.db` (`~/.local/state` when `XDG_STATE_HOME` is unset or empty), SQLite in WAL mode, schema 8. Table `agents`: name, role, job, cwd (schema 4 called it worktree), parent, report_to, task, pane_id, state (`starting`, `active`, `ended`), started_at, ended_at, last_status, last_seq, last_screen_hash, last_change_at, suspect, issue, parent_issue, thread (a thread agent's key; one live thread agent per thread). Table `threads`: thread, slug, channel, context, ticket, ticket_url, sessions, created_at. Table `inbox`: msg_id (unique), thread, state (`reserved`, `delivered`, `dropped`), received_at. Table `questions`: job (empty for a thread agent's), thread, asked_by, text, approval, state (`pending`, `answered`), asked_at, answered_at. Table `worktrees`: path, repo, branch, job, created_by, created_at, removed_at (null while the worktree is the job's). Table `jobs`: job, parent_issue, key, repo (empty for cross-repo), lead_cwd, home_thread (the caller's `FLEET_THREAD` at `job start`, the thread the job reports to), state (`open`, `ended`), outcome (empty while open, then `done` or `abandoned`), started_at, ended_at; a name and a non-empty key are unique among open jobs, and `agents` allows one live lead per parent issue. Table `steps`: key, step, done_at, unique per (key, step): the completed steps of a multi-step ending (`job-end:<jobs.id>`: `comment-work-order`, `release-work-order`, `comment-parent`, `release-parent`, `end-ledger`, `conclude`, `close-workspace`; `thread-end:<agents.id>`: `comment`, `release`, `end-row`), kept as history. `status`, `watch` and `job list` take `--target`, defaulting to `FLEET_TARGET`, then `default`; a missing ledger is exit 5.
- `$XDG_CONFIG_HOME/fleet/<target>.json` (`~/.config` when unset or empty): `linear` (`team`; absent: thread tickets are off and threads still run) and `fednet` (`socket`; absent: fleet cannot post to a thread). No file means neither; an invalid file is exit 1.
- `inbox <event-file>`: the event is `{"msg_id", "payload"}`; a payload of type `message` has `thread` (`CHANNEL/TS`), `text`, `user`, `ts`, `context` (a new thread's channel description) and an optional `target` (`default` when absent); any other type is ignored, exit 0. The herdr session is `--session`, else the target's name. Exit 0 once the thread's agent has the message (delivered to the live one, or started: `thread-<slug>`, slug the key lower-cased with runs of other characters as `-`, hashed to fit 32 characters), when the message was already handled, or when Linear was unavailable and the line was posted (message dropped); 1 for a bad event file or target; 2/3/4 as `send` on a delivery; 3 at an unknown start-up screen; 5 when herdr or the database fails, or the outage line could not be posted (fednet retries; a retry of a run killed after `agent start` finds the `starting` row and delivers the full first message). The agent's first message is `[FROM: inbox]`, the embedded prompt (role, identity, commands, where to post), `## Channel context`, `## Earlier sessions on this thread` (the `Session <n> ended` comments, oldest first) and `## The message` (`Message in thread <key> from <user> at <ts>:` and the text); later messages carry the last part only. Ticket: `atb linear create --team <team> --label thread --title <first line of the text, at most 80 characters> --description-file <channel, thread, first message, context> --json`, `atb linear claim <ticket> --agent thread-<slug> --source <key> --scope '<target>: thread <key>'`; on a reopen the claim, `atb linear comment` (`Session <n> started`) and `atb linear query` of the comments.
- `thread end --summary-file <file> [--force]` (thread agents with `FLEET_THREAD` only): with `FLEET_ISSUE`, `atb linear comment` (`Session <n> ended`, then the summary) and `atb linear release --reason done --done`; then the row is ended and the tab closed. Each step done is recorded, so a retry skips it and continues (an atb exit 4 on the retry is a failure, not a done step); the tab is found from the row's recorded pane and closed whether or not herdr still has the agent, and checked gone afterwards, so a retry after a failed close finishes. `--force` skips a failing Linear step, lists the command to finish it by hand, and does the local cleanup. Exit 1 for another caller or an empty or unreadable summary; 5 when atb fails without `--force`, or herdr or the database fails. `thread set-project <project>` and `thread relate <ISSUE>` run `atb linear set-project` and `atb linear relate` on `FLEET_ISSUE`; exit 1 without a ticket. `max_agents_per_job` (default 4, counting the lead), `resource_check` (default true), `linear` (`team` and `project`; absent means Linear is off). No file means all defaults; an unreadable or invalid file is exit 1. A cross-repo job reads no config: the defaults, and Linear on exactly when the job has a parent issue, whose team and project come from `atb linear query` (an issue without a project is refused).
- `ask-human --file <file> [--approval]` (leads and thread agents): the question is recorded pending, then for a lead delivered to the job's home thread as `inbox` delivers: to the live thread agent, headed `[FROM: <lead>]`, as `Question from <lead> for the people in thread <key>. Post it to the thread with `fednet client post`` (`--approval`: `as an approval card with `fednet client request-approval``)`; when they answer, pass the answer on with `fleet send <lead> --file <file>`.` and the text; or a thread agent is started for the thread (reopen, `Session <n> started` naming the question) with that as its first message. A thread agent's question is recorded and not delivered. Exit 1 for a worker, an empty or unreadable file, a job not open or without a home thread; 2/3/4 as `send`; 5 when Linear is unavailable for a needed start (question pending, nothing posted), or herdr or the database fails. A person's message arriving through `inbox` marks the thread's pending questions answered.
- `.fleet/config.json` in `~/dev/<repo>`: `max_agents_per_job` (default 4, counting the lead), `resource_check` (default true), `linear` (`team` and `project`; absent means Linear is off). No file means all defaults; an unreadable or invalid file is exit 1. A cross-repo job reads no config: the defaults, and Linear on exactly when the job has a parent issue, whose team and project come from `atb linear query` (an issue without a project is refused).
- `job start <job> --task-file <file> [--parent-issue <ISSUE> | --new-parent <TITLE>] [--repo <repo>] [--key <key>] [--model] [--effort]`, thread agents only; the job name `threads` is reserved. The caller's `FLEET_THREAD` becomes the job's home thread, and with Linear on its thread ticket (`FLEET_ISSUE`) is related to the parent after the work order (`atb linear relate`). With Linear on exactly one parent flag is required; `--new-parent` is refused for a cross-repo job; with Linear off both are refused. The job row and the lead's row are reserved first; then the Linear steps in order: `atb linear create --team --project --title <TITLE> --description-file <task> --json` (only with `--new-parent`), `atb linear claim <parent> --agent <job>-lead --source <caller> --scope '<repo or cross-repo>: job <job>'`, `atb linear create ... --parent <parent> --title <first non-empty task line without leading #, at most 80 characters> ...`, `atb linear claim <new> ...`. Then the lead's row gets the work order, `~/cross-repo/<job>/` is made for a cross-repo job, a workspace labelled `<job>` whose first tab is `lead`, Claude Code with the fixed arguments, the task delivered with `Work order: <url>` first. Refused (exit 1) when an open job has the name or the key, a live lead has the parent issue, the lead's name is live or in herdr, a workspace has the label, or the cross-repo directory exists; the message names what is in the way. An atb step exiting non-zero is exit 5 with what was created listed, the reserved rows included; on any failure after the reservation the output lists what exists and `fleet job end <job> --force`.
- `spawn <name> --task-file <file> --cwd <dir> [--model] [--effort]`, leads only: the worker `<job>-<name>` in a new tab of the job's workspace, in `--cwd` (an existing directory). The worker's row is reserved first (in one transaction with the name and cap checks); with Linear on the work order then goes under the job's parent issue as above, `--scope '<repo or cross-repo>: job <job>'`; a single-repo job with Linear on and no parent issue is refused. The cap counts live rows of the job including the lead.
- `job list [--target] [--json]`: one line per open job, oldest first, tab-separated `job`, `parent_issue`, `key`, `repo`, `lead`, `workers` (comma-joined live workers); `-` for an empty field; nothing when no job is open. `--json`: objects with `job`, `parent_issue`, `key`, `repo`, `lead_cwd`, `lead` (null when none is live), `workers`, `started_at`.
- `done [--report-file <file>] [--abandon]`, workers only: the message names the report file as an absolute path. With `FLEET_ISSUE` set, `--report-file` is required and comes first: `atb linear comment`, then `atb linear release --agent $FLEET_AGENT --reason done --done` (`--reason abandoned --abandon` with `--abandon`), then delivery naming the issue. An atb step exiting non-zero stops it: nothing delivered, row live, exit 5 naming the step. `--abandon` needs `FLEET_ISSUE`; a thread agent or a lead is refused (a lead ends its job with `job end`).
- `job end [<job>] --report-file <file> [--abandon]`, the job's lead only (`<job>`, when given, must be `FLEET_JOB`): refused (exit 1) while the job has live workers, naming them. With `FLEET_ISSUE`: `atb linear comment <issue> --body-file <report>`, then `atb linear release <issue> --agent <lead> --reason done --done` (`--reason abandoned --abandon` with `--abandon`); with a parent issue: `atb linear comment <parent> --body-file <conclusion>`, then the same release of the parent. The conclusion is `Job <job> ended: <done|abandoned>.` then `Lead: <lead>. Work order: <issue>. Report: <absolute path>` (no work order: that clause omitted); it is printed on stdout after `ended job <job>: <outcome>, <n> rows ended`. An atb step exiting non-zero stops it: exit 5 naming the step, nothing changed in herdr; running it again continues from the first step not recorded, including after the ledger update (the job already ended) when the workspace close failed. Something left in the way is exit 5 listing it, the job still open. `job end <job> --force` from a thread agent or a shell without `FLEET_ROLE` (a lead or worker is refused): no report file, no `--abandon`; closes the workspaces labelled `<job>`, removes the job's directories, ends its live rows and marks an open job `abandoned`; prints `reclaimed job <job>: 0 left, <n> rows ended`, then `Linear steps not done for job <job>; finish them by hand:` with one `  - ` line per step not recorded (work order comment and release when the lead has one, parent comment and release when the job has one); a job with nothing left ends 0 rows, exit 0.
- `worktree <repo> [--name <name>] [--branch <branch>]`: needs `FLEET_JOB`; makes `~/wt/<repo>/<job>[-<name>]` on a new branch `<job>[-<name>]` (or `--branch`) from origin/HEAD of `~/dev/<repo>`, without tracking, and prints only the path. The same job calling again gets the path, exit 0, nothing changed; a path that exists otherwise is refused, exit 1.
- Messages carry a first line `[FROM: <agent>]`; watch sends as `cron` to a worker's lead; inbox delivers as `inbox`.

## Known issues and next steps

The judge is green against the Go binary and is a blocking CI check. `watch`'s screen filter knows only Claude Code's screen, and its judge arm runs with a 5 s stale limit, so it is sensitive to a loaded machine. `runtime.NumCPU` honors the affinity mask, not a cgroup CPU quota, so the resource check in a quota-limited container compares the load with more CPUs than the quota allows. A delivery with no clear signal (exit 2) leaves the new agent's row `starting`, so the row does not claim a task the agent may not have; `job end --force` ends it. A lead's `job end` has no rollback: a step that fails mid-way is run again on the retry, so a comment can appear twice; and `atb linear release` is not itself resumable (its comment written, its state update failed: the retry is refused with status 4), which fleet does not repair; `job end --force` then finishes locally and names the step. `job end` ends the lead's own pane with the workspace, so the lead's last action is this command. An `inbox` run killed after its agent started is finished by fednet's retry (the row is `starting`, the full first message is delivered then); a retried exit 2 may deliver a message twice. Nothing yet ends the row of a thread agent that vanished from herdr until the thread's next message. The fednet client's hook setup is in `docs/knowledge/fednet-hook.md`.

Approval outcomes (payload type `approval`) are ignored by `inbox`; the thread agent learns the outcome from the card in the thread. `watch` does not yet remind people of pending questions.

Next: `job end`'s conclusion to the home thread through `route` once it lands; `watch` on thread agents and pending questions; `fleet report`.
