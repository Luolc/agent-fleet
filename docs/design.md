# fleet design

## What this is and is not

A CLI that runs and coordinates coding agents in herdr; not an agent itself, not a service, not a Go library.

## Model

Three roles. A **thread agent** (`thread-<slug>`, role `thread`) is one conversation on a Slack thread; it starts jobs and is the only agent that talks to people. A **lead** (`<job>-lead`) runs one job and starts workers. A **worker** (`<job>-<name>`) does one task for its lead. Each role's first message starts with fleet's built-in prompt for it (`thread_prompt.md`, `lead_prompt.md`, `worker_prompt.md` in `internal/cmd`, placeholders filled by fleet), so fleet's rules reach the agent with its task. Thread agents are started by `fleet inbox`, the fednet client's hook, when a message arrives on a thread without a live agent; they run in the herdr workspace `threads` of their scope's session (started by `inbox` through the systemd user unit `fleet-scope@<scope>` when it is not running and the thread gets an agent), one tab per thread next to a `shell` tab that runs no agent (pane `<scope>-shell`; both made or restored before each start), in the directory of the thread's channel (below). A **thread** has at most one live agent and, with a Linear team configured for the scope, one thread ticket for its whole life; each conversation on it is a session, counted on the thread's row, ended by `fleet thread end`. A session lasts while the thread waits on a person or a job (a pending question in it, or an open job whose home thread it is): the answer and the lead's messages reach the live agent, an idle session costs nothing, and a new one starts cold with the prompt, the summaries and the thread.

A **job** is the unit of work, named by its id, with at most one parent issue in Linear. It is a row in the `jobs` table from `job start` until `job end`; its lead and workers are rows in `agents`. A job is single-repo (`--repo`: the lead runs in the main checkout `<checkouts>/<repo>`, read-only by convention) or cross-repo (the lead runs in `<job>/` inside the checkout of its home thread's initiative, `<initiatives>/<I>/`, or the general initiative's for a thread of one repo; fleet makes and removes `<job>/`, never the checkout). No command makes a worktree for an agent; agents open theirs with `fleet worktree`, and a worker runs wherever its lead's `--cwd` says.

A **scope** is one fleet: the herdr session `fleet-<scope>`, one ledger and one settings file, isolated from the other scopes on the machine. The caller's scope is `--scope`, else `FLEET_SCOPE`, else `main`; `inbox` takes it from the message (the hub's per-channel `scope`, `main` when absent). The repo of a job is a job attribute, not the ledger key. A scope's own settings (what no repo can hold: the Linear team of thread tickets, the fednet socket, the machine's directories and the channel names) are in `$XDG_CONFIG_HOME/fleet/<scope>.json`.

A **channel** decides where a thread belongs (its *mapping*), by the scope's settings (below): `<repo prefix><R>` runs its thread agents in the main checkout `<checkouts>/<R>`; `<initiative prefix><I>` in `<initiatives>/<I>/`, the checkout of the initiative's repo, which has the channel's name; a direct message to the bot belongs to the general initiative, `<initiative prefix><general initiative>`. fleet makes none of these checkouts. Any other channel is ignored. A thread keeps the mapping and directory recorded at its first delivery, but its kind (repo or initiative) is read with the current prefixes, so `channels` is changed only while no thread is recorded.

## Parts and how they connect

- `cmd/fleet`: parses the command line (standard `flag`, one `FlagSet` per command, `--scope` global, `job` (with `start`, `list` and `end`) and `thread` command groups) and dispatches to `internal/cmd`; turns a failure into `fleet: <message>` on stderr and the exit code.
- `internal/cmd`: one file per command, plus `agent.go` with what the two starters share (names, the task file, the config and Linear settings of a job, the work order, places in herdr, starting Claude Code and getting it past the folder-trust dialog to its input box: only the dialog for the agent's own directory, one key per press from where the cursor is on the screen just read; a start that fails with herdr's `pane get` showing no agent in the pane (Claude Code exited, as a PATH shim does while an update reinstalls it) is made once more in the same pane after 3 s, a slow one still in the pane is not; delivery, the machine's resources). `job start` runs its checks, does the Linear steps (parent created with `--new-parent`, parent claimed for the lead, lead's work order created and claimed), writes the job row and the lead's `starting` row, makes the cross-repo job's directory and the workspace, starts the lead and delivers its first message: the lead prompt, the latest message a person posted in the home thread (from the thread's row, as one JSON line with its sender and time) and the task. `spawn` (lead only) does the same for a worker in a tab of the job's workspace, with the job's parent issue from the jobs row, its first message the worker prompt and the task. `send` adds the `[FROM: <agent>]` header and delivers through `herdr.Prompt`. `done` (workers only) delivers the report to the lead and ends the caller's row only when herdr reports it delivered; with `FLEET_ISSUE` it first writes the report to that issue and releases it through `internal/atb`. `worktree` opens `<worktrees>/<repo>/<job>[-<name>]` from origin/HEAD, or with `--detach <ref>` as a detached checkout of that commit (for a review of a PR head), and records it in the scope's ledger. `job end` (the lead, from its own pane; refused while the job has live workers) writes the report to the lead's work order and releases it, writes the conclusion to the parent issue and releases it, closes the other agents of the job's workspace, refuses while any agent but the lead has its cwd inside a recorded worktree or the cross-repo directory, removes them, ends the job with its outcome and the lead's row, hands the conclusion to `concluded` (the home-thread hook; it prints until thread agents exist) and closes the workspace last. `job end <job> --force` (a thread agent, or no `FLEET_ROLE`) reclaims a job from outside: no report, no Linear step; it closes the workspace first, cleans up with the same checks, and ends the job as `abandoned` with its live rows. `status` prints the open jobs as `job list` does, then the live rows joined with `herdr agent list`. `report` reads only the ledger's `jobs`, `threads` and `questions`. `job list` joins the open jobs with their live lead and workers. `watch` (for cron) reads each live lead's and worker's herdr status, `state_change_seq` and a hash of its screen with Claude Code's spinner, input box and footer stripped, records them, counts an agent unchanged for the stale limit (or gone from herdr) as a suspect, prints every suspect, and tells each lead as `cron` through `send`'s path only when the set of suspects among that lead's workers changes; a lead's own suspicion is only printed.
- `internal/cmd/inbox.go` and `thread.go`: `inbox` reads the event file, finds the thread's mapping from `trigger` and `channel_name` (an ignored channel opens no ledger unless the scope's ledger already knows the thread), reserves the `msg_id` in the scope's ledger (a delivered or dropped message exits 0 at once), and routes: a live thread agent gets the message through `Deliver` headed `[FROM: inbox]`; a message delivered or given to a new agent is recorded on the thread's row as the latest from a person (`last_text`, `last_user`, `last_ts`); a live row whose agent herdr no longer has is ended; otherwise, when the thread's directory exists (else one line is posted and the message dropped, as for Linear below), `threadStart` reserves the agent's row and counts the session, does the Linear steps (new thread: ticket created with `atb linear create --label thread` and claimed; known thread: claimed again, a `Session <n> started` comment, the `Session <n> ended` comments read with `atb linear query`), makes the tab in the `threads` workspace (the workspace when missing), starts Claude Code as `spawn` does and delivers the embedded prompt (`thread_prompt.md`) with the channel context, the summaries and the message. A failed Linear step means Linear is unavailable: the row is ended, the message dropped, one line posted with `fednet client post`, exit 0. `thread end` is refused while the thread waits (its pending questions and the open jobs it is home to, listed) unless `--asked-to-end`; it then writes the summary comment, releases the ticket, posts the closing line (`会话已结束 · <ticket>`, a small grey `-footer` post that also completes an open progress card; the thread and ticket come from the ledger rows, not the environment), ends the row and closes the tab last, each step recorded through `runStep` (`steps.go`) so a retry continues and the line is posted at most once; `thread post` posts a thread agent's text to the thread its live row records, through the scope's socket; `thread progress` sends the agent's whole progress card (or `--done`) the same way, keeping no card state (the hub tracks the one open card per thread and closes it before any post); `thread set-project` and `thread relate` act on `FLEET_ISSUE`. The embedded prompt names neither the thread key nor the socket: thread agents post only through fleet; it tells them to post one line on a person's message, keep a card while they work, and post the reply; the session summary has a section on what the people decided or corrected, and a job's task file carries what bears on it.
- `internal/cmd/askhuman.go`: `ask-human` records the question as pending (table `questions`; the same text asked again while pending is the same row), posts it to the job's home thread with `fednet client post`, and takes it to the thread through `route`, headed with the lead's name, so a thread agent is started for the thread when none is live; the post and the delivery are steps recorded under `ask-human:<question id>`, so a retry continues and never posts twice. A thread agent's own question is recorded and posted, not delivered. `inbox` marks a thread's pending questions answered when a person's message arrives there. `concluded` (`jobend.go`, the `conclude` step of `job end`) takes the job's conclusion to the home thread the same way, marked as a conclusion that needs no answer; a job without a home thread only prints it, and a delivery that did not succeed fails the step so a retry delivers again.
- `internal/herdr`: runs the `herdr` CLI with a bounded environment and a deadline, parses its one-object JSON reply, and maps `agent prompt` outcomes to the exit codes.
- `internal/atb`: runs `atb linear create` (only an identifier and an https URL are taken from its `--json` output; a thread ticket is labelled `thread`, a lead's work order `lead`, a worker's `worker`), `claim`, `comment`, `release`, `set-project`, `relate` and `query` through herdr's runner (deadline, process group, allow-list plus `LINEAR_API_KEY`, `LINEAR_API_KEY_CMD`, `LINEAR_API_URL`, `ATB_HOME`); the key travels only in the environment, and atb's output never goes into an error.
- `internal/fednet`: runs `fednet client post` and `client progress` through the same runner: what fleet itself says in a thread, including the closing line (`post -footer`; fednet's output hidden), and `thread post` and `thread progress` (fednet's output and exit code handed back).
- `internal/config`: a repo's `.fleet/config.json`, read from its checkout, and a scope's `<scope>.json`, with the defaults of its paths and channels; standard library only. Unknown keys and wrong types are refused, naming the key.
- `internal/db`: the ledger (`modernc.org/sqlite`, WAL, 5 s busy timeout, immediate transactions) and its schema migration.
- `internal/identity`: the caller's identity from the `FLEET_*` variables; `FLEET_THREAD` is injected only into a thread agent's pane.
- `internal/exit`: the exit-code contract and the failure type every command returns.
- `internal/cliargs`: the clap-like behaviors `flag` lacks (flags after positionals, a string flag that records whether it was given).

## Invariants

Each invariant links to the test that guards it, or is marked untested.

- The CLI behaves as the judge (`judge/`) says: argv, exit codes, stdout/stderr, ledger rows, herdr state and screens. Guarded by `judge/run.sh`; every command's cases are in `judge/usage.sh`, `send.sh`, `lifecycle.sh`, `watch.sh` and `worktree.sh` and `thread.sh`.
- `inbox` is idempotent by `msg_id`: the message is reserved before anything else, a message once delivered or dropped is never acted on again, and a rerun while the thread's agent row is live (a run killed after the start) delivers to that agent instead of starting another; one live thread agent per thread is a partial unique index. Guarded by `cmd/fleet/thread_test.go`, `internal/db/db_test.go` and `judge/thread.sh`.
- An ending (`thread end`) can always be finished: a retry skips the recorded steps and continues, so the closing line goes to the thread at most once, and `--force` finishes the local cleanup when Linear or the post keeps failing, naming what is left. Guarded by `cmd/fleet/thread_test.go` and `judge/thread.sh`.
- A thread agent's session is not ended while the thread waits on a person or a job, unless the agent says the people asked it to end (`--asked-to-end`). Guarded by `cmd/fleet/thread_test.go` and `judge/thread.sh`.
- A Linear step failing in `inbox` starts no agent; the message is acknowledged (dropped, exit 0) only once the thread has been told, else it is kept for fednet's retry. Guarded by `cmd/fleet/thread_test.go` and `judge/thread.sh`.
- A start reserves its ledger rows first, in one immediate transaction with the dedup checks (`job start`: the job row and the lead's `starting` row; `spawn`: the worker's `starting` row), then does the Linear steps (`job start`: parent, parent claim, work order, claim; `spawn`: work order, claim), and creates nothing else before they are done; an identifier is written onto the rows as soon as its issue exists, before the claim, so a failure after the reservation lists the rows, which keep the identifiers written so far, and `fleet job end <job> --force`; the key never appears in an argument, output or error. Guarded by `cmd/fleet/workorder_test.go`.
- One live lead per parent issue, one open job per name and per key in a scope: two starts cannot both pass, even concurrently, because the reservation serializes them and the partial unique indexes refuse what slips through; a parent created by `--new-parent` is bound to the rows before anything else happens; the second is refused naming the first, and a parent whose lead ended is reused. Guarded by `cmd/fleet/workorder_test.go` (a start held at its parent claim, given or just created, while another is refused) and `internal/db/db_test.go` (the indexes).
- Every refusal of `job start` and `spawn` happens before any row is written, any Linear issue created or claimed, and anything made in herdr; the checks before the reservation read only (`herdr agent list`, `herdr workspace list`, `atb linear query`). Guarded by `cmd/fleet/lifecycle_test.go`.
- `job end` removes nothing an agent (other than the lead ending its job) is still in, and never a worktree with uncommitted changes or a cross-repo directory holding a git checkout with uncommitted changes; a lead's `job end` changes nothing in herdr, and nothing in the ledger but the record of its completed Linear steps, before those steps succeeded; a retry after a failure skips the recorded steps (`runStep`), never repeating a release, and only the record counts as done (atb's refusal of an issue nobody holds is a failure); a lead whose ending marked the job ended but failed to close the workspace may run `job end` again to finish. `job end --force` finishes the local cleanup whatever Linear did, and prints the Linear steps of the open job's ending that are not recorded. Guarded by `cmd/fleet/worktree_test.go` and `lifecycle_test.go` (a stateful retry).
- `watch` tells a lead only about its own workers, and only when their suspect set changes; a blocked or missing lead is told again next run. Guarded by `cmd/fleet/watch_test.go`.
- A start presses keys only at Claude Code's folder-trust dialog, and only when it names the agent's own directory; the dialog for another directory and every other screen stop the start with exit 3 and the screen. A start (or the finishing of an interrupted one) is made at most twice, in the same pane under the same name, so a second start never runs beside a live agent and the ledger keeps one row. Guarded by `internal/cmd/agent_test.go` and `judge/lifecycle.sh`.

## Interfaces

What the judge and the tests pin down:

- Commands `inbox`, `thread post`, `thread progress`, `thread end`, `thread set-project`, `thread relate`, `ask-human`, `job start`, `job list`, `job end`, `spawn`, `send`, `done`, `status`, `report`, `watch`, `worktree`, with `--scope <name>` global (`inbox` refuses it) and `--help` on each; `--version`.
- Exit codes, shared by every command: 0 ok; 1 usage error or precondition refused; 2 no clear signal from herdr (timeout, stalled); 3 target blocked or a start stopped at an unknown screen; 4 target not found; 5 environment error (herdr, atb, git, database).
- Identity from `FLEET_AGENT`, `FLEET_ROLE` (`thread`, `lead`, `worker`), `FLEET_PARENT`, `FLEET_SCOPE`, `FLEET_JOB`, `FLEET_ISSUE` (the work order or thread ticket, empty without one), injected into every pane a start creates, plus `FLEET_THREAD` (the thread key) in a thread agent's pane only; `FLEET_WATCH_STALE_SECS` overrides watch's 30-minute limit.
- The ledger at `$XDG_STATE_HOME/fleet/<scope>.db` (`~/.local/state` when `XDG_STATE_HOME` is unset or empty), SQLite in WAL mode, schema 10. Table `agents`: name, role, job, cwd (schema 4 called it worktree), parent, report_to, task, pane_id, state (`starting`, `active`, `ended`), started_at, ended_at, last_status, last_seq, last_screen_hash, last_change_at, suspect, issue, parent_issue, thread (a thread agent's key; one live thread agent per thread). Table `threads`: thread, slug, channel, context, ticket, ticket_url, sessions, created_at, mapping (the channel's name, or the general initiative's for a direct message), cwd (both fixed at the first delivery), last_text, last_user, last_ts (the latest message a person posted, as `inbox` delivered it). Table `inbox`: msg_id (unique), thread, state (`reserved`, `delivered`, `dropped`), received_at. Table `questions`: job (empty for a thread agent's), thread, asked_by, text, approval, state (`pending`, `answered`), asked_at, answered_at. Table `worktrees`: path, repo, branch (empty for a detached checkout), job, created_by, created_at, removed_at (null while the worktree is the job's). Table `jobs`: job, parent_issue, key, repo (empty for cross-repo), lead_cwd, home_thread (the caller's `FLEET_THREAD` at `job start`, the thread the job reports to), state (`open`, `ended`), outcome (empty while open, then `done` or `abandoned`), started_at, ended_at; a name and a non-empty key are unique among open jobs, and `agents` allows one live lead per parent issue. Table `steps`: key, step, done_at, unique per (key, step): the completed steps of a multi-step ending (`job-end:<jobs.id>`: `comment-work-order`, `release-work-order`, `comment-parent`, `release-parent`, `end-ledger`, `conclude`, `close-workspace`; `thread-end:<agents.id>`: `comment`, `release`, `footer`, `end-row`), kept as history. `status`, `watch` and `job list` read the caller's scope; a missing ledger is exit 5.
- `$XDG_CONFIG_HOME/fleet/<scope>.json` (`~/.config` when unset or empty): `linear` (`team`; absent: thread tickets are off and threads still run), `fednet` (`socket`; absent: neither fleet nor `thread post` can post to a thread), `paths` and `channels`. `paths`, absolute or `~/` (`HOME`): `checkouts` (default `~/dev`), the repos' main checkouts; `initiatives` (`~/x-repo`), the initiatives' checkouts; `worktrees` (`~/wt`), where `worktree` makes its worktrees; `scratch` (`~/scratch`), named in the prompts for the agents' files. `channels`, `[a-z0-9_-]`, neither prefix starting the other: `repo_prefix` (`repo-`), `initiative_prefix` (`x-repo-`, also the prefix of an initiative's repo), `general_initiative` (`general`), the initiative of direct messages. A key left out keeps its default, an empty or `null` one is refused (as is a `null` section, or a file that is not a JSON object); no file means all defaults; an invalid file is exit 1 (`inbox` reads it before deciding whether to serve a channel). The prompts show a path under `HOME` as `~/...`. Changing `paths.initiatives` while a cross-repo job is open leaves its `<job>/` behind at `job end`: it is removed only when still under `initiatives`.
- `inbox <event-file>`: the event is `{"msg_id", "payload"}`; a payload of type `message` has `thread` (`CHANNEL/TS`), `text`, `user`, `ts`, `context` (a new thread's channel description), and optional `trigger` (`dm` for a direct message), `channel_name` and `scope` (`main` when absent, `[a-z0-9-]`); any other type is ignored, exit 0, as is a message whose channel has neither prefix and is not a direct message, for a thread the scope does not know. Exit 0 once the thread's agent has the message (delivered to the live one, or started: `thread-<slug>`, slug the key lower-cased with runs of other characters as `-`, hashed to fit 32 characters), when the message was already handled, or when the thread's directory is missing or Linear was unavailable and a line saying so was posted (message dropped); 1 for a bad event file or scope; 2/3/4 as `send` on a delivery; 3 at an unknown start-up screen; 5 when herdr or the database fails, or the outage line could not be posted (fednet retries; a retry of a run killed after `agent start` finds the `starting` row and delivers the full first message). The agent's first message is `[FROM: inbox]`, the embedded prompt (role, identity, the thread's mapping and directory, how to choose between a single-repo and a cross-repo job, commands, where to post, finding out why a command failed before asking), `## Channel context`, `## Earlier sessions on this thread` (the `Session <n> ended` comments, oldest first) and `## The message` (`Message in thread <key> from <user> at <ts>:` and the text); later messages carry the last part only. Ticket: `atb linear create --team <team> --label thread --title <first line of the text without the mentions it starts with (`<@U…>`), at most 80 characters> --description-file <channel, thread, first message, context> --json`, `atb linear claim <ticket> --agent thread-<slug> --source <key> --scope '<mapping>: thread <key>'`; on a reopen the claim, `atb linear comment` (`Session <n> started`) and `atb linear query` of the comments.
- `thread post --body-file <file> [--attach <path>]...` (thread agents with a live row only): `fednet client post -socket <fednet.socket> -thread <the row's thread> [-file <path>]... -- <text>`, the text as the file has it (whitespace only counts as empty), as an argument with no shell between; fednet's stdout printed, no retry. Exit 1 for another caller, a row whose thread is not `FLEET_THREAD`, an unreadable or empty body or one over 102400 bytes, no socket; fednet's exit code and stderr as they are when the post fails; 5 when fednet cannot run or times out.
- `thread progress --title <text> [--item <text>:<doing|done|error>]...` or `thread progress --done [--title <text>] [--item ...]...` (thread agents with a live row only): `fednet client progress -socket <socket> -thread <the row's thread> [-done] [-title <text>] [-item <item>]...`, the whole card each call (the hub keeps one open card per thread, replaced whole; `-done` closes it, with the wording given); fednet's stdout printed, no retry. Exit 1 for another caller, no title without `--done`, over 50 items, an item without one of the three states, or no socket; fednet's exit code and stderr as they are when the call fails; 5 when fednet cannot run or times out.
- `thread end --summary-file <file> [--force] [--asked-to-end]` (thread agents with `FLEET_THREAD` only): refused, before any step, while a question in the row's thread is pending (`questions`) or a job with it as `home_thread` is open, each listed (`question from <asker>, pending: <first line, at most 80 characters>`, `job <job>, open, reporting to this thread`); `--asked-to-end` skips that check (only when the people in the thread asked to end; `--force` does not). Then, with `FLEET_ISSUE`, `atb linear comment` (`Session <n> ended`, then the summary) and `atb linear release --reason done --done`; then, with a socket, `fednet client post -socket <socket> -thread <the row's thread> -footer -- 会话已结束 · [<ticket>](<url>)` (`会话已结束` without a ticket; a note and no post without a socket); then the row is ended and the tab closed. Each step done is recorded, so a retry skips it and continues (an atb exit 4 on the retry is a failure, not a done step); the tab is found from the row's recorded pane and closed whether or not herdr still has the agent, and checked gone afterwards, so a retry after a failed close finishes. `--force` skips a failing Linear step, lists the command to finish it by hand, skips a failing closing line saying so, and does the local cleanup. Exit 1 for another caller, an empty or unreadable summary, or a thread that waits without `--asked-to-end`; 5 when atb or the post fails without `--force`, or herdr or the database fails. `thread set-project <project>` and `thread relate <ISSUE>` run `atb linear set-project` and `atb linear relate` on `FLEET_ISSUE`; exit 1 without a ticket.
- `ask-human --file <file> [--approval]` (leads and thread agents): the question is recorded pending and posted to the thread by fleet, then for a lead delivered to the job's home thread as `inbox` delivers: to the live thread agent, headed `[FROM: <lead>]`, as `Question from <lead> for the people in thread <key>, already posted there by fleet; when they answer, pass the answer on with `fleet send <lead> --file <file>`.` and the text; or a thread agent is started for the thread (reopen, `Session <n> started` naming the question) with that as its first message. A thread agent's question is recorded and posted, not delivered. The question keeps its text but for trailing whitespace. Rerunning with the same pending question skips the recorded `post` and `deliver` steps and says when nothing was done; a failure says what is recorded and to ask again. Exit 1 for `--approval` (approval cards are not supported yet; the flag is kept so the refusal names it), a worker, an empty or unreadable file, a job not open or without a home thread, no fednet socket (nothing recorded); 2/3/4 as `send`; 5 when the post fails (question pending, not delivered) or Linear is unavailable for a needed start (question posted and pending), or herdr or the database fails. A person's message arriving through `inbox` marks the thread's pending questions answered.
- `.fleet/config.json` in the main checkout (or the initiative checkout, below): `max_agents_per_job` (default 16, counting the lead), `resource_check` (default true), `linear` (`team` and `project`; absent means Linear is off). No file means all defaults; an unreadable or invalid file is exit 1. A single-repo job reads it in the lead's directory, the main checkout recorded at `job start`. A cross-repo job reads the same file in its initiative checkout (the parent of the lead's directory), refused the same way, but not its `linear`: Linear is on exactly when the job has a parent issue, whose team and project come from `atb linear query` (an issue without a project is refused).
- `job start <job> --task-file <file> [--parent-issue <ISSUE> | --new-parent <TITLE>] [--repo <repo>] [--key <key>] [--model] [--effort]`, thread agents only; the job name `threads` is reserved. The caller's `FLEET_THREAD` becomes the job's home thread, and with Linear on its thread ticket (`FLEET_ISSUE`) is related to the parent after the work order (`atb linear relate`). With Linear on exactly one parent flag is required; `--new-parent` is refused for a cross-repo job; with Linear off both are refused. The job row and the lead's row are reserved first; then the Linear steps in order: `atb linear create --team --project --title <TITLE> --description-file <task> --json` (only with `--new-parent`), `atb linear claim <parent> --agent <job>-lead --source <caller> --scope '<repo or cross-repo>: job <job>'`, `atb linear create ... --parent <parent> --label lead --title <first non-empty task line without leading #, at most 80 characters> ...`, `atb linear claim <new> ...`. Then the lead's row gets the work order, `<job>/` is made in the cross-repo root (above; its checkout must exist, else exit 1 before anything) for a cross-repo job, a workspace labelled `<job>` whose first tab is `lead`, Claude Code with the fixed arguments, and the first message delivered headed `[FROM: <caller>]`: the lead prompt (identity, where it runs, the job's Linear state, the agent cap, `<scratch>/<repo>` or `<scratch>/<initiative prefix><I>` for its files, which part of the message speaks for a person, how to start workers (an implementer in a worktree the lead opens first) and what a task file carries (the people's decisions and corrections, routes ruled out, what must hold before the next step, when to stop), follow them and change route after two reports without progress, finish what is inside the goal before ending, decide on and make merges itself after an LGTM, read from the reviewer's verdict comment on the PR rather than the message, with `--match-head-commit`, once the PR's acceptance record and the reviewer's failing-test line check out against the approved head, find out why a command failed before asking, look for an earlier answer before asking the people, ask them and end), `## Latest message from a person in the home thread` (one JSON object `{"user", "ts", "text"}` from the thread's row, the text as written, so no newline or heading in it ends the section; or a line saying none is recorded), and `## Your task` (`Work order: <url>` when the lead has one, then the task file as it is, to the end: fleet places the heading, so the task cannot move where it begins, and a record-shaped block inside it stays inside it). Refused (exit 1) when an open job has the name or the key, a live lead has the parent issue, the lead's name is live or in herdr, a workspace has the label, or the cross-repo directory exists; the message names what is in the way. An atb step exiting non-zero is exit 5 with what was created listed, the reserved rows included; on any failure after the reservation the output lists what exists and `fleet job end <job> --force`.
- `spawn <name> --task-file <file> --cwd <dir> [--model] [--effort]`, leads only: the worker `<job>-<name>` in a new tab of the job's workspace, in `--cwd` (an existing directory). The worker's row is reserved first (in one transaction with the name and cap checks); with Linear on the work order then goes under the job's parent issue as above with `--label worker`, `--scope '<repo or cross-repo>: job <job>'`; a single-repo job with Linear on and no parent issue is refused. The cap counts live rows of the job including the lead. The first message, headed `[FROM: <lead>]`, is the worker prompt (identity, where it runs, messages and their exit codes, the report file, what an implementer (an acceptance record in the PR: what ran, at which head, its output line, what did not run), a reviewer (revert the change and show the new test fail) and a researcher do, that merging is the lead's, when to stop and report, which steps need a person's yes through the lead, finding out why a command failed before asking, `done` (the report also names the routes ruled out and what must hold before the next step), and pushing or saving as a patch what is worth keeping before `--abandon`) and `## Your task` as for a lead.
- `job list [--all] [--json]`: the open jobs of the caller's scope whose home thread has the caller's mapping (a thread agent's own thread, a lead's or worker's job's home thread), or all of them with `--all` or for a caller with no thread; one line per job, oldest first, tab-separated `job`, `parent_issue`, `key`, `repo`, `lead`, `workers` (comma-joined live workers); `-` for an empty field; nothing when no job is open. `--json`: objects with `job`, `parent_issue`, `key`, `repo`, `lead_cwd`, `lead` (null when none is live), `workers`, `started_at`.
- `report [--json]`: read-only, from the ledger alone. One line per job, open and ended, in start order, with its state (`open`, its outcome, or `unknown` for a question whose job has no row), the jobs that asked nothing included; one line per thread for the questions its thread agent asked (`job` empty), only for threads with such a question; then the total. Each line: questions asked, answered and pending, and the median and longest wait of the answered ones (`answered_at - asked_at`). A question counts for the latest job of its name started by the time it was asked, since a name is unique only among open jobs; a rerun of `ask-human` while its question is pending adds no row. `answered_at` is when `inbox` took the next message a person posted in the thread, which marks every question pending there answered: the wait runs to that message, not necessarily to the answer. `--json` is `{"jobs": [...], "threads": [...], "total": {...}}`, waits in seconds, null when nothing was answered.
- `done [--report-file <file>] [--abandon]`, workers only: the message names the report file as an absolute path. With `FLEET_ISSUE` set, `--report-file` is required and comes first: `atb linear comment`, then `atb linear release --agent $FLEET_AGENT --reason done --done` (`--reason abandoned --abandon` with `--abandon`), then delivery naming the issue. An atb step exiting non-zero stops it: nothing delivered, row live, exit 5 naming the step. `--abandon` needs `FLEET_ISSUE`; a thread agent or a lead is refused (a lead ends its job with `job end`).
- `job end [<job>] --report-file <file> [--abandon] [--close-parent done|abandoned]`, the job's lead only (`<job>`, when given, must be `FLEET_JOB`): refused (exit 1) while the job has live workers, naming them. With `FLEET_ISSUE`: `atb linear comment <issue> --body-file <report>`, then `atb linear release <issue> --agent <lead> --reason done --done` (`--reason abandoned --abandon` with `--abandon`); with a parent issue: `atb linear comment <parent> --body-file <conclusion>`, then `atb linear release <parent> --agent <lead> --reason 'job <job> ended'`, which gives back the claim `job start` took and returns the parent to the state it had before that claim (atb cannot release and keep the current state), so a later job can take it; only `--close-parent` closes it, with the release `--done` or `--abandon` as above. `--abandon` is the job's own outcome and leaves the parent alone; `--close-parent` on a job without a parent issue, or with another value, is refused (exit 1). The conclusion is `Job <job> ended: <done|abandoned>.` then `Lead: <lead>. Work order: <issue>. Report: <absolute path>` (no work order: that clause omitted); it is printed on stdout after `ended job <job>: <outcome>, <n> rows ended`. With a home thread it is delivered there as `ask-human` delivers (headed with the lead's name, marked a conclusion), by the recorded `conclude` step. An atb step exiting non-zero stops it: exit 5 naming the step, nothing changed in herdr; running it again continues from the first step not recorded, including after the ledger update (the job already ended) when the workspace close failed. Something left in the way is exit 5 listing it, the job still open. `job end <job> --force` from a thread agent or a shell without `FLEET_ROLE` (a lead or worker is refused): no report file, no `--abandon`, no `--close-parent`; closes the workspaces labelled `<job>`, removes the job's directories, ends its live rows and marks an open job `abandoned`; prints `reclaimed job <job>: 0 left, <n> rows ended`, then `Linear steps not done for job <job>; finish them by hand:` with one `  - ` line per step not recorded (work order comment and release when the lead has one, parent comment and release when the job has one); a job with nothing left ends 0 rows, exit 0.
- `worktree <repo> [--name <name>] [--branch <branch> | --detach <ref>]`: needs `FLEET_JOB`; makes `<worktrees>/<repo>/<job>[-<name>]` on a new branch `<job>[-<name>]` (or `--branch`) from origin/HEAD of the checkout `<checkouts>/<repo>` or, when there is none and `<repo>` is `<initiative prefix><I>`, `<initiatives>/<I>` (else exit 1 naming both), without tracking, or with `--detach` as a detached checkout of `<ref>` (resolved in the checkout after `git fetch origin`; no branch, so `job end` deletes none), and prints only the path; `job end` finds the checkout a worktree came from with `git rev-parse --git-common-dir`. The same job calling again gets the path, exit 0, nothing changed; a path that exists otherwise, `--detach` with `--branch`, or a ref that names no commit is refused, exit 1.
- Messages carry a first line `[FROM: <agent>]`; watch sends as `cron` to a worker's lead; inbox delivers as `inbox`.

## Known issues and next steps

The judge is green against the Go binary and is a blocking CI check. `watch`'s screen filter knows only Claude Code's screen, and its judge arm runs with a 5 s stale limit, so it is sensitive to a loaded machine. `runtime.NumCPU` honors the affinity mask, not a cgroup CPU quota, so the resource check in a quota-limited container compares the load with more CPUs than the quota allows. A delivery with no clear signal (exit 2) leaves the new agent's row `starting`, so the row does not claim a task the agent may not have; `job end --force` ends it. A lead's `job end` has no rollback: a step that fails mid-way is run again on the retry, so a comment can appear twice; and `atb linear release` is not itself resumable (its comment written, its state update failed: the retry is refused with status 4), which fleet does not repair; `job end --force` then finishes locally and names the step. `job end` ends the lead's own pane with the workspace, so the lead's last action is this command. An `inbox` run killed after its agent started is finished by fednet's retry (the row is `starting`, the full first message is delivered then); a retried exit 2 may deliver a message twice. Nothing yet ends the row of a thread agent that vanished from herdr until the thread's next message, when `inbox` finds the agent gone and ends the row; that ending posts no closing line (the grey `-footer` post saying the session ended) and leaves an open progress card open (`watch` on thread agents would mark it `-error`). The judge has no systemd: a fake `systemctl` starts the session, so the real unit is checked only by hand (`docs/knowledge/fednet-hook.md`). The fednet client's hook setup is in `docs/knowledge/fednet-hook.md`.

Approval cards are not supported yet: `ask-human --approval` is refused, fleet posts questions as plain text, and `inbox` ignores payloads of type `approval`. Routing a card's outcome by `approval_id` to its pending question (kept pending until then) is a follow-up. `watch` does not yet remind people of pending questions, and nothing yet reclaims a thread agent's session left idle while its thread waits.

Next: `watch` on thread agents and pending questions; `report` counting repeated questions in a thread (needs a text similarity).
