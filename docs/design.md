# fleet design

## What this is and is not

A CLI that runs and coordinates coding agents in herdr; not an agent itself, not a service, not a Go library.

## Model

Three roles. A **thread agent** (role `thread`) is one conversation on a Slack thread; it starts jobs. A **lead** (`<job>-lead`) runs one job and starts workers. A **worker** (`<job>-<name>`) does one task for its lead. Nothing starts thread agents yet; a thread agent is any caller with `FLEET_ROLE=thread`.

A **job** is the unit of work, named by its id, with at most one parent issue in Linear. It is a row in the `jobs` table from `job start` until `close`; its lead and workers are rows in `agents`. A job is single-repo (`--repo`: the lead runs in `~/dev/<repo>`, read-only by convention) or cross-repo (the lead runs in `~/cross-repo/<job>/`, which fleet makes and removes). No command makes a worktree for an agent; agents open theirs with `fleet worktree`, and a worker runs wherever its lead's `--cwd` says.

A **target** names one ledger: `FLEET_TARGET`, `default` when unset or empty. A development machine has one target; a machine that hosts several datasets has one per dataset. The repo of a job is a job attribute, not the ledger key.

## Parts and how they connect

- `cmd/fleet`: parses the command line (standard `flag`, one `FlagSet` per command, `--session` global, `job` a command group with `start` and `list`) and dispatches to `internal/cmd`; turns a failure into `fleet: <message>` on stderr and the exit code.
- `internal/cmd`: one file per command, plus `agent.go` with what the two starters share (names, the task file, the config and Linear settings of a job, the work order, places in herdr, starting Claude Code and getting it past the folder-trust prompt to its input box, delivery, the machine's resources). `job start` runs its checks, does the Linear steps (parent created with `--new-parent`, parent claimed for the lead, lead's work order created and claimed), writes the job row and the lead's `starting` row, makes the cross-repo directory and the workspace, starts the lead and delivers the task. `spawn` (lead only) does the same for a worker in a tab of the job's workspace, with the job's parent issue from the jobs row. `send` adds the `[FROM: <agent>]` header and delivers through `herdr.Prompt`. `done` delivers the report to `FLEET_PARENT` and ends the caller's row only when herdr reports it delivered; with `FLEET_ISSUE` it first writes the report to that issue and releases it through `internal/atb`. `worktree` opens `~/wt/<repo>/<job>[-<name>]` from origin/HEAD and records it in the target's ledger. `close` (thread agents only; refused while the job has live rows unless `--force`) closes the workspace, refuses while an agent's cwd is inside a recorded worktree or the cross-repo directory, removes them, and ends the job and its rows only when nothing is left. `status` joins the live rows with `herdr agent list`. `job list` joins the open jobs with their live lead and workers. `watch` (for cron) reads each live lead's and worker's herdr status, `state_change_seq` and a hash of its screen with Claude Code's spinner, input box and footer stripped, records them, counts an agent unchanged for the stale limit (or gone from herdr) as a suspect, prints every suspect, and tells each lead as `cron` through `send`'s path only when the set of suspects among that lead's workers changes; a lead's own suspicion is only printed.
- `internal/herdr`: runs the `herdr` CLI with a bounded environment and a deadline, parses its one-object JSON reply, and maps `agent prompt` outcomes to the exit codes.
- `internal/atb`: runs `atb linear create` (only an identifier and an https URL are taken from its `--json` output), `claim`, `comment`, `release` and `query` (a parent's team key and project name) through herdr's runner (deadline, process group, allow-list plus `LINEAR_API_KEY`, `LINEAR_API_KEY_CMD`, `LINEAR_API_URL`, `ATB_HOME`); the key travels only in the environment, and atb's output never goes into an error.
- `internal/config`: a repo's `.fleet/config.json`, read from its main checkout `~/dev/<repo>`; standard library only. Unknown keys and wrong types are refused, naming the key.
- `internal/db`: the ledger (`modernc.org/sqlite`, WAL, 5 s busy timeout, immediate transactions) and its schema migration.
- `internal/identity`: the caller's identity from the `FLEET_*` variables.
- `internal/exit`: the exit-code contract and the failure type every command returns.
- `internal/cliargs`: the clap-like behaviors `flag` lacks (flags after positionals, a string flag that records whether it was given).

## Invariants

Each invariant links to the test that guards it, or is marked untested.

- The CLI behaves as the judge (`judge/`) says: argv, exit codes, stdout/stderr, ledger rows, herdr state and screens. Guarded by `judge/run.sh`; every command's cases are in `judge/usage.sh`, `send.sh`, `lifecycle.sh`, `watch.sh` and `worktree.sh`.
- A start reserves its ledger rows first, in one immediate transaction with the dedup checks (`job start`: the job row and the lead's `starting` row; `spawn`: the worker's `starting` row), then does the Linear steps (`job start`: parent, parent claim, work order, claim; `spawn`: work order, claim), and creates nothing else before they are done; the key never appears in an argument, output or error. A failure after the reservation lists the rows and `fleet close <job> --force`. Guarded by `cmd/fleet/workorder_test.go`.
- One live lead per parent issue, one open job per name and per key in a target: two starts cannot both pass, even concurrently, because the reservation serializes them and the partial unique indexes refuse what slips through; the second is refused naming the first, and a parent whose lead ended is reused. Guarded by `cmd/fleet/workorder_test.go` (a start held at its parent claim while another is refused) and `internal/db/db_test.go` (the indexes).
- Every refusal of `job start` and `spawn` happens before herdr or atb is called and before any row is written. Guarded by `cmd/fleet/lifecycle_test.go`.
- `close` removes nothing an agent is still in, and never a worktree with uncommitted changes. Guarded by `cmd/fleet/worktree_test.go` and `lifecycle_test.go`.
- `watch` tells a lead only about its own workers, and only when their suspect set changes; a blocked or missing lead is told again next run. Guarded by `cmd/fleet/watch_test.go`.

## Interfaces

What the judge and the tests pin down:

- Commands `job start`, `job list`, `spawn`, `send`, `done`, `status`, `watch`, `close`, `worktree`, with `--session <name>` global and `--help` on each; `--version`.
- Exit codes, shared by every command: 0 ok; 1 usage error or precondition refused; 2 no clear signal from herdr (timeout, stalled); 3 target blocked or a start stopped at an unknown screen; 4 target not found; 5 environment error (herdr, atb, git, database).
- Identity from `FLEET_AGENT`, `FLEET_ROLE` (`thread`, `lead`, `worker`), `FLEET_PARENT`, `FLEET_TARGET`, `FLEET_JOB`, `FLEET_ISSUE` (the work order, empty without one), injected into every pane a start creates; `FLEET_WATCH_STALE_SECS` overrides watch's 30-minute limit.
- The ledger at `$XDG_STATE_HOME/fleet/<target>/fleet.db` (`~/.local/state` when `XDG_STATE_HOME` is unset or empty), SQLite in WAL mode, schema 5. Table `agents`: name, role, job, cwd (schema 4 called it worktree), parent, report_to, task, pane_id, state (`starting`, `active`, `ended`), started_at, ended_at, last_status, last_seq, last_screen_hash, last_change_at, suspect, issue, parent_issue. Table `worktrees`: path, repo, branch, job, created_by, created_at, removed_at (null while the worktree is the job's). Table `jobs`: job, parent_issue, key, repo (empty for cross-repo), lead_cwd, home_thread (reserved for the thread the job reports to), state (`open`, `ended`), outcome (empty, `done`, `abandoned`; `close` leaves it empty), started_at, ended_at; a name and a non-empty key are unique among open jobs, and `agents` allows one live lead per parent issue. `status`, `watch` and `job list` take `--target`, defaulting to `FLEET_TARGET`, then `default`; a missing ledger is exit 5.
- `.fleet/config.json` in `~/dev/<repo>`: `max_agents_per_job` (default 4, counting the lead), `resource_check` (default true), `linear` (`team` and `project`; absent means Linear is off). No file means all defaults; an unreadable or invalid file is exit 1. A cross-repo job reads no config: the defaults, and Linear on exactly when the job has a parent issue, whose team and project come from `atb linear query` (an issue without a project is refused).
- `job start <job> --task-file <file> [--parent-issue <ISSUE> | --new-parent <TITLE>] [--repo <repo>] [--key <key>] [--model] [--effort]`, thread agents only. With Linear on exactly one parent flag is required; `--new-parent` is refused for a cross-repo job; with Linear off both are refused. The job row and the lead's row are reserved first; then the Linear steps in order: `atb linear create --team --project --title <TITLE> --description-file <task> --json` (only with `--new-parent`), `atb linear claim <parent> --agent <job>-lead --source <caller> --scope '<repo or cross-repo>: job <job>'`, `atb linear create ... --parent <parent> --title <first non-empty task line without leading #, at most 80 characters> ...`, `atb linear claim <new> ...`. Then the lead's row gets the work order, `~/cross-repo/<job>/` is made for a cross-repo job, a workspace labelled `<job>` whose first tab is `lead`, Claude Code with the fixed arguments, the task delivered with `Work order: <url>` first. Refused (exit 1) when an open job has the name or the key, a live lead has the parent issue, the lead's name is live or in herdr, a workspace has the label, or the cross-repo directory exists; the message names what is in the way. An atb step exiting non-zero is exit 5 with what was created listed, the reserved rows included; on any failure after the reservation the output lists what exists and `fleet close <job> --force`.
- `spawn <name> --task-file <file> --cwd <dir> [--model] [--effort]`, leads only: the worker `<job>-<name>` in a new tab of the job's workspace, in `--cwd` (an existing directory). The worker's row is reserved first (in one transaction with the name and cap checks); with Linear on the work order then goes under the job's parent issue as above, `--scope '<repo or cross-repo>: job <job>'`; a single-repo job with Linear on and no parent issue is refused. The cap counts live rows of the job including the lead.
- `job list [--target] [--json]`: one line per open job, oldest first, tab-separated `job`, `parent_issue`, `key`, `repo`, `lead`, `workers` (comma-joined live workers); `-` for an empty field; nothing when no job is open. `--json`: objects with `job`, `parent_issue`, `key`, `repo`, `lead_cwd`, `lead` (null when none is live), `workers`, `started_at`.
- `done [--report-file <file>] [--abandon]`: the message names the report file as an absolute path. With `FLEET_ISSUE` set, `--report-file` is required and comes first: `atb linear comment`, then `atb linear release --agent $FLEET_AGENT --reason done --done` (`--reason abandoned --abandon` with `--abandon`), then delivery naming the issue. An atb step exiting non-zero stops it: nothing delivered, row live, exit 5 naming the step. `--abandon` needs `FLEET_ISSUE`; a thread agent (no parent) is refused.
- `close <job> [--force]`, thread agents only: as described above; marks the job ended without an outcome.
- `worktree <repo> [--name <name>] [--branch <branch>]`: needs `FLEET_JOB`; makes `~/wt/<repo>/<job>[-<name>]` on a new branch `<job>[-<name>]` (or `--branch`) from origin/HEAD of `~/dev/<repo>`, without tracking, and prints only the path. The same job calling again gets the path, exit 0, nothing changed; a path that exists otherwise is refused, exit 1.
- Messages carry a first line `[FROM: <agent>]`; watch sends as `cron` to a worker's lead.

## Known issues and next steps

The judge is green against the Go binary and is a blocking CI check. `watch`'s screen filter knows only Claude Code's screen, and its judge arm runs with a 5 s stale limit, so it is sensitive to a loaded machine. `runtime.NumCPU` honors the affinity mask, not a cgroup CPU quota, so the resource check in a quota-limited container compares the load with more CPUs than the quota allows. A delivery with no clear signal (exit 2) leaves the new agent's row `starting`, so the row does not claim a task the agent may not have; `close --force` ends it.

Next: `job end` (the lead ends its job with a report and a conclusion on the parent issue; it replaces `close`), `done` for workers only, `status` per job; then thread agents, their lifecycle, and the job's home thread (`jobs.home_thread`), through which a lead's suspicion and the job's conclusion reach a person.
